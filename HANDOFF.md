# HANDOFF

This document is everything needed to pick up VeriFace on a different
machine (target: an RTX Pro 6000 / H200-class GPU) and run it end-to-end.
It was written during a restructure/hardening pass done in an environment
with **no GPU and no dataset available** — nothing that required either was
run. Every number in this document is either directly quoted from the
original codebase's own logged output, or explicitly marked as an estimate
or an open question. Nothing is fabricated.

---

## Dataset Required

**Identified datasets** (from `archive/notebooks/split_dataset.ipynb`, the
only place in the repo that names them): **DFDC** (Deepfake Detection
Challenge), **FaceForensics++ ("FF")**, and **Celeb-DF** (collected but
explicitly excluded from training in the original code — kept as an
optional external held-out set).

No dataset **version** (e.g. FF++ compression level c0/c23/c40, which DFDC
release) is recorded anywhere in the codebase. Treat this as **UNKNOWN —
needs external research / asking whoever ran the original training**.

### Expected directory structure

The code (`src/data/build_splits.py`, née `split_dataset.ipynb`) reads from:

```
<VERIFACE_DATASET_DIR>/                    (default: <repo_root>/Dataset/)
├── DFDC_REAL_Face_only_data/<video_stem>/...
├── DFDC_FAKE_Face_only_data/<video_stem>/...
├── FF_Face_only_data/
│   ├── <video_stem>/...
│   └── metadata.csv                       (optional)
├── Celeb_real_face_only/<video_stem>/...  (optional, held out — not used for training)
└── Celeb_fake_face_only/<video_stem>/...  (optional, held out — not used for training)
```

**Known inconsistency, not resolved by guessing:** the original notebook's
markdown docstring says these folders live under `preprocessed/`, but the
actual code reads them from `Dataset/`. This restructure trusts the code
(`Dataset/`) as authoritative, matching `src/config.py`'s `DATASET_DIR`
default — but if you're handed a folder tree that instead matches the old
markdown (`preprocessed/...`), that's the doc, not a different pipeline
version; point `VERIFACE_DATASET_DIR` wherever the real folders actually are.

**Resolved**: `src/data/preprocess_raw.py` is the raw-video → `*_Face_only_data`
step that was previously missing from this repo entirely. It takes a folder
of raw `.mp4`/`.mov`/`.avi` files for one dataset+label at a time, samples
`src.config.FRAMES_PER_VIDEO` frames per video, MTCNN-crops faces (same
detector config as `src/data/face_crop.py`), and writes directly into the
`*_Face_only_data` layout `src/data/build_splits.py` expects — see "Exact
Run Order" below (now Step 0) and "What Changed" for details. It has only
been validated with tiny synthetic videos in this environment (see
`tests/test_preprocess_raw.py`) — never against real DFDC/FF++/Celeb-DF
downloads, since none are available here.

### Label file

`data/labels.json` (generated by `src/data/build_splits.py`): flat JSON
`{"<video_stem>": 0}` (real) or `{"<video_stem>": 1}` (fake). Duplicate
stems across sources are disambiguated with a `__<source>` suffix (e.g.
`"005_010__ffpp"`).

### Filename convention (needed for leakage prevention)

FaceForensics++ manipulated-video stems encode two identities:
`<target_id>_<source_id>` (e.g. `005_010` — confirmed against real committed
notebook output: `check_embeddings.ipynb` inspects `embeddings/train/005_010.npy`).
DFDC entries in this project were reindexed to bare integers (e.g. `837`,
also confirmed from real committed output) with **no preserved link back to
DFDC's own `metadata.json`** — searched every notebook/script/README for
`metadata.json`, `dfdc_train_part`, `"original"`, `identity`, `actor_id`,
`source_id`, `target_id`: zero hits. This is why
`src/eval/leakage_check.py` can only verify FF++-side identity leakage, and
says so explicitly in its own report output.

### Where to obtain it

Not recorded anywhere in this codebase. DFDC, FaceForensics++, and Celeb-DF
are all publicly documented research datasets with their own access/request
processes — this needs external research (their official pages/request
forms), not guessing from this code.

## Environment Requirements

### GPU / CUDA

- Target: RTX Pro 6000 (Blackwell, compute capability sm_120) or H200-class.
- Pinned `torch==2.13.0` / `torchvision==0.28.0`, installed from the
  `cu129` (CUDA 12.9) wheel index — confirmed to exist as real, current
  PyPI/wheel-index packages as of 2026-08-16 (checked via `pip index
  versions` and the PyTorch wheel index directly; not guessed). **Not
  verified against real Blackwell hardware from this environment** — before
  relying on this, confirm at https://pytorch.org/get-started/locally/ that
  this build still lists sm_120 support, since GPU compatibility can't be
  checked from here.
- VRAM: EfficientNet-B3 at 224×224, batch size 32, mixed precision, is
  typically a 6–10 GB training footprint; the Bi-LSTM temporal model
  (hidden=512, 2 layers, embeddings as input) is well under 2 GB even at
  batch size 16. Both are **estimates based on the model sizes and batch
  sizes found in the original training code**, not measured here. An RTX
  Pro 6000's 96 GB VRAM has enormous headroom over either — if anything,
  consider raising batch size for faster training rather than worrying
  about fitting.

### Storage (estimated, not measured)

The only real, logged dataset-size evidence in the repo is from
`archive/notebooks/check_embeddings.ipynb`'s committed output: **4066 train
+ 761 val + 255 test = 5082 videos** at the time that notebook was last run.
Using that as the reference `n`:

| Stage | Per-video | Estimated total (n≈5082) |
|---|---|---|
| Raw dataset (DFDC+FF+++Celeb-DF originals) | dataset-dependent | **unknown — depends on which DFDC/FF++ release; do not guess, check official dataset page sizes** |
| `preprocessed/frames/` (8 JPEGs/video, quality 100, ~224px) | ~150–250 KB | ~1 GB |
| `embeddings/` (`[8, 1536]` float32 `.npy`) | ~48 KB | ~250 MB |
| `checkpoints/spatial/` (EfficientNet-B3 + optimizer state on `_last`) | ~55 MB (`_best`, no optimizer) / ~180 MB (`_last`, with AdamW state) | n/a (fixed, not per-video) |
| `checkpoints/temporal/` | ~40–60 MB per checkpoint | n/a |
| `checkpoints/ensemble/` | <1 MB | n/a |

These are rough, formula-based estimates (frame count × typical JPEG size,
embedding shape × 4 bytes, parameter count × 4 bytes), not measurements.
The raw dataset size is the one line item that actually matters for disk
provisioning and it's the one this repo has zero evidence for — check the
official DFDC/FF++/Celeb-DF pages before provisioning storage.

## Exact Run Order

0. **`python -m src.data.preprocess_raw --input-dir <raw_videos> --output-dir Dataset/ --dataset-name {dfdc,ffpp,celebdf} --label {real,fake} --workers <N>`**
   Turns a folder of raw video files into the `*_Face_only_data` layout
   Step 1 (`build_splits.py`) expects — this is the "Step 0" that used to be
   entirely missing from this repo (see "Dataset Required" above). **Run it
   once per (dataset, label) combination** — six invocations total to cover
   the full pipeline, since DFDC and Celeb-DF have separate real/fake input
   folders and FF++ needs both labels processed (into the same output
   folder — see below):

   ```bash
   python -m src.data.preprocess_raw --input-dir raw/dfdc_real    --output-dir Dataset/ --dataset-name dfdc    --label real --workers 8
   python -m src.data.preprocess_raw --input-dir raw/dfdc_fake    --output-dir Dataset/ --dataset-name dfdc    --label fake --workers 8
   python -m src.data.preprocess_raw --input-dir raw/ffpp_real    --output-dir Dataset/ --dataset-name ffpp    --label real --workers 8
   python -m src.data.preprocess_raw --input-dir raw/ffpp_fake    --output-dir Dataset/ --dataset-name ffpp    --label fake --workers 8
   python -m src.data.preprocess_raw --input-dir raw/celebdf_real --output-dir Dataset/ --dataset-name celebdf --label real --workers 8
   python -m src.data.preprocess_raw --input-dir raw/celebdf_fake --output-dir Dataset/ --dataset-name celebdf --label fake --workers 8
   ```

   For `ffpp`, both commands write into the same `Dataset/FF_Face_only_data/`
   folder and merge rows into `Dataset/FF_Face_only_data/metadata.csv` (this
   is how `build_splits.py` recovers FF++ labels — see "What Changed"
   below) — run both real and fake before moving on to Step 1.

   Every corrupt/unreadable video, video shorter than the configured frame
   count, and video with zero detected faces is appended to
   `logs/preprocessing_failures.log` (configurable via `--failures-log`) —
   check that file after each run; a large failure count usually means
   `--device`/codec support needs attention before trusting the rest of the
   pipeline. Runtime: not measured in this environment (no real dataset or
   GPU here) — expect this to be the most I/O- and CPU-bound stage of the
   whole pipeline given per-frame MTCNN inference across possibly hundreds
   of thousands of frames; `--workers` should be set close to available CPU
   core count for a real dataset run.

1. **`python -m src.data.build_splits --check-leakage`**
   Builds identity-grouped train/val/test splits + `data/labels.json`, then
   immediately runs the leakage checker and fails (non-zero exit) if any
   identity group spans multiple splits. Runtime: seconds to low minutes —
   pure filesystem listing + a small grouping/bin-packing pass, no model
   inference. **Run this first, before anything else** — it's the gate the
   original codebase never had.

2. **`python -m src.data.extract_frames --splits train val test`**
   Samples 8 frames/video into `preprocessed/frames/<split>/<stem>/`.
   Runtime: roughly linear in video count and I/O speed; the original code
   gives no timing reference, so this is unestimated — expect it to be I/O
   bound, not compute bound.

3. **`python -m src.train.train_spatial`**
   Trains EfficientNet-B3 on extracted frames. Default 12 epochs, batch
   size 32. No wall-clock reference exists for this stage in the original
   codebase's logged output (only the *temporal* stage happened to have
   timed epochs logged — see stage 5). Expect this to be the single most
   time-consuming stage given EfficientNet-B3's cost relative to the tiny
   Bi-LSTM in stage 5.

4. **`python -m src.data.extract_embeddings`**
   Uses the newly-trained spatial backbone to compute per-frame embeddings
   for every video → `embeddings/<split>/<stem>.npy`. Runtime similar in
   shape to stage 2 (mostly forward passes + I/O, no backprop).

5. **`python -m src.train.train_temporal`**
   Trains the Bi-LSTM+attention model on embeddings. Default 25 epochs,
   batch size 16. **This is the one stage with a real logged runtime
   reference**, from `archive/notebooks/train_temporal_debugging.ipynb`'s
   committed output: **~3.3–3.8 seconds/epoch** on whatever GPU that
   notebook was run on (unspecified) — so ~25 epochs ≈ **under 2 minutes**
   on comparable hardware, likely faster on an RTX Pro 6000. That same
   output also showed `train_auc=1.0000` from epoch 0 — see "Known
   Limitations" below before trusting the resulting val/test AUC.

6. **`python -m src.train.train_ensemble`**
   Fits the calibrated logistic regression on 5-feature rows built from
   spatial+temporal outputs. Trivial compute cost (a few thousand rows, 5
   features, scikit-learn `LogisticRegression` + `CalibratedClassifierCV`)
   — seconds, dominated by the embedding-loading loop, not the fit itself.
   Writes `checkpoints/ensemble/ensemble_final.joblib` and the `accuracy`
   section of `results/metrics.json`.

7. **`python -m src.eval.benchmark --videos-dir <path/to/sample_videos>`**
   Measures real end-to-end latency (decode + face detection + all three
   models) on the target GPU, over however many sample videos you point it
   at. Writes the `latency` section of `results/metrics.json`. No runtime
   estimate exists for this — it's new, replacing a marketing claim that was
   never measured at all (see "What Changed" below).

8. **`streamlit run app/main.py`**
   Launches the app. Reads `results/metrics.json` for the hero
   accuracy/latency badges — shows "pending" until stages 6 and 7 have
   actually produced it.

## What Changed From the Original Codebase

**Structure**
- All 10 original notebooks + the old `app.py` + the old
  `src/process_data/*.py` scripts moved to `archive/` unmodified (see
  `archive/README.md`). Nothing was deleted.
- Notebook-sprawl consolidated into `src/{data,models,train,inference,eval}`
  + `app/`, one canonical script per pipeline stage, importable via
  `python -m src.<package>.<module>`.
- `notebooks/extract_frames.ipynb` (split-aware, actually used by the rest
  of the pipeline) and `archive/legacy_src_process_data/extract_frames.py`
  (a generic, split-unaware duplicate) merged into one
  `src/data/extract_frames.py`.
- `train_ensemble.ipynb` (defensive: bad-data logging, adaptive calibration
  folds) and `train_ensemble3.ipynb` (simpler) merged into one
  `src/train/train_ensemble.py`, keeping the defensive behavior.
- The app's temporal model (unmasked, unpacked — only correct by
  coincidence at batch size 1) and the training script's temporal model
  (masked, packed — correct for batched variable-length training) merged
  into one `src/models/temporal.py` where `lengths` is an optional
  parameter; `tests/test_models.py` asserts the two call styles are
  numerically equivalent.
- **New: `src/data/preprocess_raw.py`** — the raw-video → `*_Face_only_data`
  step that had no equivalent anywhere in the original codebase (old or
  archived). Samples `config.FRAMES_PER_VIDEO` frames per video (a new
  constant added to `src/config.py`, mirroring
  `src/data/extract_frames.py`'s own `FRAMES_PER_VIDEO_DEFAULT` so the value
  isn't duplicated as a second hardcoded literal), reuses the exact MTCNN
  configuration `src/data/face_crop.py` uses (`keep_all=False,
  select_largest=True` — hand-kept in sync since `face_crop.py` itself
  wasn't touched), and writes straight into the folder layout
  `build_splits.py` expects. Runs in parallel via a `multiprocessing.Pool`
  (`--workers`), and appends every corrupt/unreadable/no-face/short-video
  case to a dedicated failures log rather than skipping silently. See
  `tests/test_preprocess_raw.py` (18 tests, synthetic videos, CPU-only,
  including a real multi-worker run) and "Exact Run Order" (now Step 0).
  Also writes `FF_Face_only_data/metadata.csv` for `--dataset-name ffpp` —
  otherwise the label this stage assigns would be unrecoverable, since
  `build_splits.py`'s fallback label-inference (checking for "fake"/"real"
  in the parent folder path) can never match FF++'s single fixed
  `FF_Face_only_data` dirname. That fallback quirk was left as-is
  (`build_splits.py` wasn't touched) — `preprocess_raw.py` just makes sure
  the metadata.csv path always works instead.

**Correctness fixes**
- **Checkpoint contract bug (the main one)**: training saved a bare sklearn
  object to `ensemble_best.pkl`; the app expected a `{"calibrator": ...}`
  dict at `ensemble_final.joblib`. Loading a real trained checkpoint would
  have raised `TypeError: 'CalibratedClassifierCV' object is not
  subscriptable`. Fixed by `src/models/checkpoint.py`: one save/load schema
  (for both torch and ensemble checkpoints), imported by every training
  script and by `src/inference/pipeline.py`. Regression-tested in
  `tests/test_checkpoint_schema.py` (including a test that reproduces the
  exact original bug shape and asserts it now raises a clear error instead
  of silently loading wrong).
- **Silent random-weight fallback**: `app.py` had a bare `except: pass`
  around checkpoint loading. `src/inference/pipeline.py`'s `load_models`
  now returns an explicit per-component load status; `ModelBundle.critical_ok`
  must be true before `analyze_video` will run at all — otherwise it raises
  `ModelsNotReadyError`. The app shows this as a visible error state, not a
  silent degraded prediction.
- **Dead "frames to sample" slider**: the original UI slider set
  `st.session_state.n_frames` but extraction ignored it (hardcoded
  `FRAMES_TO_SAMPLE = 20`). `extract_faces(video_path, mtcnn, n_frames=...)`
  now takes it as a real parameter, and `app/main.py` passes the slider
  value through.
- **Fabricated latency/accuracy claims removed**: `"sub-250ms verdicts with
  99.2% accuracy"` (hardcoded strings, never computed from anything —
  see KNOWLEDGE_BASE.md for the original audit) is gone. The app reads
  `results/metrics.json` (via `src.eval.metrics.load_metrics`) and shows an
  explicit "not yet evaluated" / "not yet benchmarked" badge when a section
  is missing — which it is, in this checkout, on purpose.
- **`face_crop.py` numeric bug**: `face.permute(1,2,0).int().numpy().astype('uint8')`
  could wrap incorrectly for any out-of-range float value; changed to
  `.clamp(0, 255).byte()`.
- **Broken `import cv2ngrok`**: the notebook's advanced app variant had this
  typo (would crash on startup). The new `app/main.py` doesn't import ngrok
  at all — tunneling was a separate, unrelated notebook cell that has no
  business being in the app module.
- **Duplicated ensemble feature-vector construction**: the 5-feature build
  (`spatial_mean/max/std/top3, temporal_logit`) existed independently (and
  subtly differently ordered/named) in `app.py`, `train_ensemble.ipynb`, and
  `train_ensemble3.ipynb`. Now one function,
  `src.models.ensemble.build_ensemble_features`.

**Dependencies / APIs**
- `torch.cuda.amp.autocast`/`GradScaler` (deprecated) → `torch.amp.autocast(device_type=...)`.
- `fpdf` (unmaintained PyPI package) → `fpdf2` (actively maintained,
  same `from fpdf import FPDF` import name — only `app/report.py` needed a
  docstring note, no code changes).
- All dependency versions in `requirements.txt` verified to actually exist
  on PyPI (via `pip index versions`) as of 2026-08-16, not guessed.

**Behavior changes worth knowing about**
- `src/train/train_spatial.py` no longer writes a `spatial_epoch_N.pth`
  snapshot every epoch (the original did) — only `_last` (resumable) and
  `_best` (by val AUC). This was a deliberate disk-usage simplification; if
  you want full per-epoch history back, it's a small addition to
  `save_torch_checkpoint` calls in the training loop.
- `src/data/build_splits.py` no longer does a flat seeded shuffle-then-slice
  split. It groups videos by identity first (see "Known Limitations" for
  what that grouping can and can't detect) and greedily bin-packs whole
  groups into train/val/test/reserved to hit the target size fractions.
  This is **not** exact stratified sampling — see the module docstring.

## What Still Needs Real Hardware to Complete

- **`src/data/preprocess_raw.py` has never been run against real raw
  video files.** Validated only against tiny synthetic videos generated
  with `cv2.VideoWriter` (solid-color frames, no real face) — this
  genuinely exercises the "corrupt file" and "no face detected" failure
  paths with the real MTCNN detector, and (via a mocked detector) the
  output folder/file-naming and `metadata.csv` logic, plus a real
  multi-worker `multiprocessing.Pool` run — but never a real photo/video, a
  GPU, or dataset-scale volume (thousands of videos). Smoke-test on a
  handful of real videos per dataset before running it over a full corpus.
- **`src/eval/leakage_check.py` has never been run** — there's no dataset
  here to run it against. Written and unit-tested against synthetic
  filenames only (`tests/test_leakage_check.py`).
- **A corrected retrain** (via the new identity-grouped
  `src/data/build_splits.py`) has never been run. The existing checkpoints
  referenced anywhere in the archived notebooks were trained on the *old*,
  leakage-unsafe splits.
- **`src/eval/benchmark.py` has never been run** — `results/metrics.json`
  does not exist in this checkout. No latency number should be trusted
  until this is run on the actual target GPU with a representative set of
  sample videos.
- **`src/train/train_ensemble.py`'s accuracy output has never been
  produced** on the corrected splits — the "accuracy" section of
  `results/metrics.json` is likewise absent.
- **No code here has been run against real video files, real checkpoints, or
  a real GPU.** What *was* actually verified in this environment (CPU-only,
  no dataset):
  - `ruff check .` — clean, zero findings.
  - `pytest` (45 tests) — all pass. CPU-only, synthetic/tiny tensors and
    mocked I/O throughout (`tests/`), including 18 tests for
    `src/data/preprocess_raw.py` against synthetic videos (real MTCNN CPU
    inference, real `multiprocessing.Pool` with `--workers 2`).
  - `app/report.py`'s `build_pdf_report` — smoke-tested directly with a
    synthetic `InferenceResult`/`VideoMeta`; produces a valid PDF (`%PDF-`

  - `streamlit run app/main.py` — actually launched (with no checkpoints
    present, i.e. exercising the "engine not ready" degraded path) and
    served HTTP 200 with no traceback in the server log.
  None of that touches a real checkpoint, a real video file, or CUDA —
  smoke-test the full pipeline on one or two real videos, with real
  checkpoints, on the target GPU, before trusting it at scale.

## Known Limitations / Open Questions

- **DFDC identity leakage is undetectable with current information.** No
  `metadata.json` (DFDC's own real/fake source mapping) survived into this
  project. `src/eval/leakage_check.py` treats every DFDC-style stem as its
  own opaque identity and says so in its report — a "clean" result only
  covers FF++-side leakage.
- **The raw-video → `*_Face_only_data` preprocessing step is no longer
  missing** — see `src/data/preprocess_raw.py` and "Exact Run Order" Step 0.
  It has not, however, been validated against real DFDC/FF++/Celeb-DF
  downloads (no dataset in this environment) — only tiny synthetic videos.
  Two things to double-check on first real use: (1) that raw dataset videos
  actually decode cleanly with this environment's OpenCV/ffmpeg build (real
  DFDC/FF++ releases use a mix of codecs); (2) that `--n-frames`'s default
  (`config.FRAMES_PER_VIDEO = 8`) is still what you want for a from-scratch
  preprocessing run — it was chosen to match `extract_frames.py`'s existing
  default, not re-derived from first principles.
- **Greedy identity-group bin-packing is not exact stratified sampling.**
  `assign_groups_to_splits` in `src/data/build_splits.py` is a deterministic
  size-balanced heuristic, not a solved stratification problem — check the
  `label_counts` it reports in `data/data_manifest.yaml` after running it;
  if class balance across splits looks meaningfully skewed, that's visible
  in the manifest, not hidden, but may need a manual look.
- **Suspicious training metrics in the archived notebooks**: `train_auc =
  1.0000` from epoch 0 through all 25 epochs of temporal training
  (`archive/notebooks/train_temporal_debugging.ipynb`), with val/test AUC
  around 0.99 as well. This may simply mean the task was easy on the old
  (leakage-unsafe) splits — or it may mean identity leakage inflated it.
  This is exactly why stage 1 (`build_splits --check-leakage`) and a full
  retrain are listed as required before trusting any accuracy number this
  pipeline produces going forward.
- **Original notebook numbering has gaps.** Comments reference stages "01"
  (split), "02" (extract_frames), "04" (train_spatial), "06"
  (train_temporal), "07" (train_ensemble) — "03" and "05" are never named.
  They may correspond to face-cropping and embedding extraction
  respectively (both of which do exist as separate notebooks/scripts), or
  there may be an undocumented step that never made it into any committed
  file. Not resolved — flagging rather than guessing.
- **RTX Pro 6000 / Blackwell CUDA compatibility** for the pinned
  `torch==2.13.0+cu129` build was checked for wheel *existence* (it exists,
  confirmed against the real PyTorch wheel index), not for actual
  Blackwell/sm_120 runtime compatibility — there is no GPU here to verify
  that. Double-check against PyTorch's official install matrix before
  relying on it.
- **`fpdf` → `fpdf2` swap**: smoke-tested in this environment with a
  synthetic `InferenceResult`/`VideoMeta` fed through `app/report.py`'s
  `build_pdf_report` — produces a valid PDF. Not tested with a real,
  model-produced `InferenceResult` (e.g. real per-frame score distributions,
  longer per-frame score lists) — worth a quick real-data check early on the
  new machine, but the basic API surface is confirmed working.
- **`opencv-python-headless` major version bump (4.x → 5.x)**: the specific
  APIs used here (`cv2.VideoCapture`, `cv2.CAP_PROP_FRAME_COUNT`,
  `cv2.cvtColor`, `cv2.COLOR_BGR2RGB`) are foundational and have been stable
  across OpenCV major versions for a decade, but this combination was not
  smoke-tested against a real video file in this environment.
- **Frame-count mismatch between training and inference is intentional but
  worth knowing about**: training extraction samples 8 frames/video
  (`src/data/extract_frames.py`); inference defaults to 20
  (`src/inference/pipeline.py`, user-adjustable 8–40 via the app slider).
  This was true in the original code too — not something this restructure
  introduced — but it means the temporal model at inference time sees
  longer sequences than it was trained on. Not necessarily wrong (attention
  pooling handles variable length), just not something to assume away.
